# 工程场景演练：故障排查 20 题

这是「学会—应用—验证」闭环的第三层（工程场景）。前两层在每份知识文档里（示例亲手跑=动手，自测=记忆），本档训练的是**真实工作里最难的那种能力**：面对一个只有现象没有答案的问题，从哪里开始想。

## 怎么用本档（初学者必读）

- 每道题先**遮住排查步骤**，只读「场景」段，自己口述排查路径，再对照。说不出第一步就先学对应文档（每题标了）。
- 排查步骤的写法是通用的四拍：**先确认现象 → 缩小范围 → 验证假设 → 修复并防复发**。背熟这四拍，比背 20 个答案值钱。
- 场景大多能用本机 LinkForge 复现（题目标了「可复现」）。能亲手复现的，一定要跑一遍：排查能力只长在手上。
- 目标不是背答案，是练出「遇到没见过的故障也不慌」的肌肉。

## 数据库类

### 场景 1：接口突然从 50ms 变 5s（可复现）

现象：跳转接口平时很快，某天起大部分请求 3–5 秒。
先想三问：全慢还是个别慢（范围）？从什么时候开始（变更点）？依赖里谁可疑（DB/缓存/MQ）？
排查：看监控指标先分层——如果只有这个接口慢，看它的 P95 是否同时涨；开慢 SQL 日志或对嫌疑 SQL 跑 EXPLAIN；检查是不是新查询没走索引（type=ALL、rows 巨大）。
修复：补索引或改写 SQL，复测。防复发：慢日志阈值常开。
对照项目：`idx_click_link_time` 就是为「按链接查时间段」这类查询建的；[40-mysql.md](40-mysql.md)。
过关：能说出「先分层再钻取」为什么比「上来就看代码」快。

### 场景 2：两个请求同时创建同码短链，一个成功了（可复现）

现象：并发测试里两个请求用同一个自定义码创建，返回一个 200 一个 409，有人说是 bug。
排查：先问「业务上允许吗」——同一码只能有一条是需求；再看服务端怎么处理冲突：捕获 `DuplicateKeyException` 转成 409 是**设计**不是事故。
认知：这是「唯一索引兜底并发」的正确表现。真正的 bug 是反过来的——两个都 200 了。
对照项目：`uk_code` + 撞码重试；机制见 [40-mysql.md](40-mysql.md)，决策五段见 [82-linkforge-decisions.md](82-linkforge-decisions.md)。
过关：能解释为什么「先查后插」挡不住这个并发。

### 场景 3：长事务把连接池拖光了

现象：应用日志出现大量「connection is not available, request timed out」。
排查：看 Hikari 的活跃连接数指标；找谁占着连接不放——典型是事务里调了外部 HTTP（本项目 webhook relay 就有出站调用，但它在事务外，这就是对比）。
修复：事务里只留 DB 操作，外部调用挪出去；必要时调大池（治标）。
对照项目：`@Transactional` 只有 recordClick/register 两处，都是纯 DB；[30-spring-core.md](30-spring-core.md)。
过关：能说出「事务边界=连接占用时间」这句话的因果。

### 场景 4：修改没生效，事务没回滚？（可复现）

现象：一个 `@Transactional` 方法里先更新 A 表再调用同类里的另一个方法 B，B 抛异常，A 却提交了。
排查：先确认调用方式——`this.b()` 是自调用，走的是原对象不是代理，事务拦截器根本没参与。这是「事务失效四坑」里最常见的一个。
修复：拆类或注入自身代理。验证：故意制造异常看回滚。
对照项目：全仓库只有两处 `@Transactional` 且写法规避了四坑；[30-spring-core.md](30-spring-core.md)。
过关：能画出「代理调用 vs 自调用」的两条路径图。

## 缓存类

### 场景 5：禁用的短链还在跳（可复现）

现象：管理员禁用了某条短链，用户仍然能跳转，持续了一小段时间。
排查：禁用接口做了什么——更新 DB、删缓存、1 秒后延迟再删一次；用户此刻的旧值来自哪一层缓存。
认知：最终一致窗口 ≈1 秒是**声明过的设计**（延迟双删），不是 bug；如果禁用后永久能跳才是 bug（说明缓存没失效或行读没兜底）。
对照项目：写穿+双删+「行是真相」；[50-redis.md](50-redis.md)。
过关：能画出那 1 秒里的读写竞态时序图。

### 场景 6：某个热点链接被疯转，DB 突然压力暴涨

现象：某短码上了热搜，平时 DB 每秒几十次行读，现在每秒上万。
排查：确认每层防线在工作——限流挡了多少（`ratelimit.rejected`）、Bloom 与缓存命中率、singleflight 合并效果（`singleflight.shared`）。
修复：防线齐了压力自然被压住；若还是高，说明行读漏了合并（比如 singleflight 配置被关）。
对照项目：五层防线每层一个指标；[50-redis.md](50-redis.md)。
过关：能按指标顺序说出「压力在哪一层被吃掉」。

### 场景 7：Redis 挂了，服务还能用吗（可复现）

现象：运维把 Redis 容器停了，用户投诉没来，但你很慌。
排查与认知：分组件看——限流 fail-open（照常服务，`ratelimit.failopen` 计数涨）、Bloom/absent 探测 fail-open（回源 DB）、缓存 miss（行读兜底）、唯一不能用的是「依赖 Redis 的强语义」（本项目没有）。**限流是保护措施不是安全边界**，所以放行。
对照项目：`docker compose stop redis` 可完整演练；[50-redis.md](50-redis.md)。
过关：能说出「哪些 fail-open、为什么指标必须同时涨」。

## 消息类

### 场景 8：MQ 断了 10 分钟，点击统计会丢吗（可复现）

现象：RabbitMQ 容器停了 10 分钟，恢复后要向老板解释数据完整性。
排查：分两个写路径看——跳转 302 不经过 MQ（点击落在 outbox 行里），relay 恢复后自动追平；这就是 Outbox 存在的理由。跑一遍 `mq-drill.sh` 代替口头解释。
对照项目：[51-rabbitmq-outbox.md](51-rabbitmq-outbox.md) 全链。
过关：能不看笔记说出「302 返回前数据在哪、恢复后怎么动」。

### 场景 9：同一条消息被消费了两次，统计多算了吗

现象：broker 重投（ack 丢失是正常现象），日志里同一 eventId 出现两次。
排查与认知：看消费端——先插去重表撞主键就跳过，重放安全。如果多算了，检查 eventId 是否确定性生成（随机 UUID 每次都不同，去重就失效）。
对照项目：eventId 两态设计；[51-rabbitmq-outbox.md](51-rabbitmq-outbox.md)。
过关：能解释「at-least-once 为什么不可怕」。

### 场景 10：DLQ 里堆了几百条消息

现象：监控发现死信队列有积压。
排查：先看消息内容分类——全是同一类异常（代码 bug）还是随机异常（下游抖动）；代码 bug 就修代码后重放，抖动就修下游。**不要直接丢弃**，DLQ 的意义就是留证据。
修复与防复发：修完后逐条或批量回放；给 DLQ 加告警。
过关：能说出「为什么不 requeue 回原队列」（热循环打满 CPU）。

### 场景 11：定时任务突然不跑了

现象：outbox 积压指标开始涨，relay 好像没在工作。
排查：调度线程池是否被某个慢任务占满（本项目池 size 6、按故障域隔离就是为了这个）；任务方法有没有吞异常退出循环；开关配置是否被改（relay-enabled）。
对照项目：`@Scheduled` 任务全部 catch 异常保循环；[13-concurrency.md](13-concurrency.md) 的线程池隔离。
过关：能说出「为什么 relay 和 webhook relay 不能共享一个线程」。

## JVM 类

### 场景 12：应用 OOM 了，怎么查（可复现）

现象：进程还在但接口全 500，日志有 OutOfMemoryError: Java heap space。
排查：前提是启动参数带 `-XX:+HeapDumpOnOutOfMemoryError`；用 MAT 打开堆转储看支配树——谁占最多、被谁引用。常见嫌疑：静态集合只增不减、ThreadLocal 未清理、大结果集一次性加载。
对照项目：本机复现做法见 [12-jvm.md](12-jvm.md) 的堆 OOM 复现一节。
过关：能说出「泄漏的本质是该死不死的对象还可达」。

### 场景 13：CPU 100% 但 QPS 没涨

现象：CPU 打满，流量却正常，说明白烧了。
排查：`top -H -p <pid>` 找线程（Windows 上用 Process Explorer 看线程，或先 `jstack` 全量抓）→ 线程号转 16 进制在栈里对号 → 区分业务死循环、频繁 GC、锁自旋。
Windows 注意：`top` 不存在于 Git Bash；等价物是任务管理器详细信息页/Process Explorer + jstack 组合。
过关：能在 5 分钟内定位到一个具体线程的栈。

### 场景 14：启动直接失败，日志一大串依赖注入报错（可复现）

现象：`java -jar` 后看到 Unsatisfied dependency、Error starting Tomcat context 等几十行。
排查：**从最后一个 `Caused by` 读起**——上面的都是转述。真实案例：最底下是 Access denied（口令错），上面那一串 apiKeyService→apiKeyMapper 只是「谁在等一个没建成的对象」的链条，别去改那些类。
Windows 注意：`.env` 只对当前终端生效，换窗口要重新导出（见仓库 README）。
对照项目：本机 2026-10-26 的真实启动失败案例；[21-os.md](21-os.md)。
过关：能解释为什么「第一个失败的 Bean」不一定是「出问题的组件」。

## Spring 类

### 场景 15：接口返回 401，但用户明明带了 token

现象：前端说带了 Authorization 头，后端返回 401。
排查：看 401 是谁返回的——过滤器链里三过滤器各有职责：token 过期/签名错（JwtAuthFilter 的 JwtException）、路径不匹配角色（403 才对）、带的是 API Key 却打在 JWT 面（400 ambiguous）。抓包确认头真的带上了、格式是 `Bearer ` 前缀。
对照项目：三过滤器编排与授权矩阵；[32-spring-security.md](32-spring-security.md)。
过关：能按状态码反推出是认证失败还是授权失败。

### 场景 16：改了配置但不生效

现象：改了 yml 里的限流阈值，重启后没变化。
排查：配置优先级链——命令行参数 > 环境变量 > yml。先看是不是被环境变量盖了（本项目所有阈值都有 `LINKFORGE_*` env 形态）；再看改的是不是正确的 profile 段（dev 段的配置在 prod profile 下不加载）。
对照项目：`application.yml` 三段结构与 `linkforge.*` 集中绑定；[31-spring-boot-mvc.md](31-spring-boot-mvc.md)。
过关：能按优先级链从高到低列出排查顺序。

### 场景 17：启动时 Bean 循环依赖报错

现象：加了一个新 Service 后启动报「circular dependency」。
排查：先看依赖方向——A 要 B、B 要 A 多半是职责没拆；把公共逻辑抽到第三个类，或一方改 `@Lazy`（治标，标注理由）。注意 Boot 2.6+ 默认直接拒绝，这是保护不是麻烦。
对照项目：依赖图是 DAG，从未触发；[30-spring-core.md](30-spring-core.md) 三级缓存一节。
过关：能说出「构造器注入为什么救不了循环依赖」。

## 安全类

### 场景 18：有人枚举短码探测别人链接

现象：日志里大量 404，同一个 IP 打不同的随机码。
排查与认知：这正是 Bloom 层设计的目的——从未创建的码在内存层就 404，不碰 DB；再往上是限流在挡量；越权查询统一 404 防枚举。三层配合，攻击者拿不到「哪些码存在」的信息。
对照项目：`bloom.rejected` 与 `ratelimit.rejected` 指标会同时涨；[32-spring-security.md](32-spring-security.md)。
过关：能按攻击路径说出每一层「拦了什么、漏了什么」。

### 场景 19：服务器时间差 8 小时引发的连环怪

现象：统计报表的日期对不上，重试任务像是「睡着了」。
排查：先分别打印 JVM 时区与 MySQL 时区（`SELECT NOW()` vs `LocalDateTime.now()`）；本项目的规则「调度时间字段用 DB 时钟，业务时间戳用 JVM 时钟」就是从真实事故里长出来的。
对照项目：Bw2-M1 故障全记录；[51-rabbitmq-outbox.md](51-rabbitmq-outbox.md)。
过关：能复述那次 20 秒变 8 小时的完整因果链。

## 综合类

### 场景 20：新同事说「这个项目到处是缓存和队列，太复杂了吧」

这是场景题也是表达题：面对「为什么这么复杂」的质疑，按「每一层解决什么问题、不解决会怎样」逐层回答（限流挡量→Bloom 挡穿透→空值缓存挡确认过的不存在→缓存省读→singleflight 合并行读→行读保真相→Outbox 保不丢）。答不出任何一层的「不解决会怎样」，那一层对你就是过度设计——这正好是检验自己理解的镜子。
过关：把这段讲成 3 分钟连贯的话并录音。

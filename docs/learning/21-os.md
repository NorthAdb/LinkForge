# 操作系统基础：一次 HTTP 请求前后的 OS 全程

优先级 P1，目标层级 L2（概念讲清、常用排查命令会用、知道每个命令在读 OS 的哪块机制）。LinkForge 不直接调用系统 API，但它的每个运行现象（进程、端口、连接、文件描述符、内存占用）都是 OS 概念的落地。

## 先说人话（初学者第一遍从这里读）

操作系统回答「你的程序凭什么能跑」：谁给它内存、谁让它上 CPU、它的数据怎么发到网卡。第一遍带走三件事：

1. **进程是资源单位，线程是干活单位**。进程领到一份独立的虚拟地址空间和文件描述符表；线程是进程里被 CPU 轮流执行的执行流。后端的并发话题（线程池、锁、上下文切换）几乎都发生在线程层。
2. **一次 HTTP 请求从头到尾 OS 都在场**：网卡收包、把连接放进队列、唤醒某个线程、替线程读 socket、把响应拷出去。每一跳都是后文的某个小节。
3. **排查命令不是背出来的，是按 OS 机制理解的**：`ss` 在读内核的连接表，`top` 在读调度统计，`free` 在读物理页的记账。理解了机制，命令忘了还能查；不理解，背了也读不懂输出。

本机是 Windows 的同学：每个命令都给了 Windows 等价物，但面试口径背 Linux 版。

## 学习目标

- 解释「一次 HTTP 请求到达 Java 进程前后，操作系统都做了什么」，说出每一步对应的 OS 机制。
- 区分进程与线程，说出上下文切换什么时候发生、贵在哪里。
- 说出用户态与内核态是什么、系统调用的代价从哪来。
- 理解阻塞 IO 阻塞在哪、多路复用解决了什么、Tomcat 的线程模型到底是什么。
- 会读 load 平均值与 top 的 CPU 列；会区分 RSS、JVM 堆、容器内存限额与 OOMKill。
- 理解文件描述符与 fd 泄漏；理解 sendfile 少做哪两次拷贝。

## 一次请求到达前后：OS 参与的七个动作

先把本项目的物理形态钉住。`docker-compose.yml` 里定义了 mysql、redis、rabbitmq 三个容器（各带 healthcheck，每 10 秒探活一次），外加一个可选的 observability profile（prometheus、grafana，默认不启动）。**应用本身不在 compose 里**：JVM 在宿主机上直接跑，文件注释原话是 the app is not containerized。所以一次请求涉及「一个宿主机 JVM 进程 + 三个容器进程」，四个进程是排查问题时的第一张图。

现在浏览器访问 `http://localhost:8080/r/abc123`（本项目跳转接口）。按时间顺序，OS 在七个动作里出场：

1. **网卡收到 TCP 包，内核收完**。包从网卡进来，内核协议栈校验、组装，全程没有一行 Java 代码参与。此时数据躺在内核为这个 socket 准备的接收缓冲区里。
2. **内核按端口找到监听者**。应用启动时调用过 `bind(8080)` 和 `listen(8080)`（Tomcat 帮它调的），内核把 8080 的连接放进这个监听 socket 的就绪队列。连接的两端视角不同：应用以为对端是 localhost，MySQL 眼中的客户端却是网桥网关地址（本项目上一版实测启动日志里有 `Access denied for user 'linkforge'@'172.18.0.1'`，`172.18.0.1` 就是 Docker 网桥上 MySQL 看到的来源）。同一个 TCP 连接，两端看到的名字可以不同。
3. **多路复用器报告「有连接可读」**。Tomcat 里有个专门盯连接的线程叫 Poller，它通过 epoll（概念见第 4 节）用一次系统调用就知道哪些连接有数据了，不用为每条连接派一个线程去傻等。
4. **上下文切换：工作线程上场**。Poller 把就绪的连接交给 Tomcat 线程池里的一个工作线程。线程被唤醒、上 CPU，是调度器干的事（第 2 节）。
5. **系统调用：把数据搬进 Java**。工作线程调用 `read()`，从用户态陷入内核态（第 3 节），内核把 socket 缓冲区的字节拷进 JVM 的字节数组。HTTP 请求行和头是 Tomcat 在这些字节上解析出来的（框架行为）。
6. **业务处理：更多的 fd、更多的阻塞**。本项目跳转路径要查 Redis、查 MySQL。每条到 Redis/MySQL 的连接都是进程文件描述符表里的一项（第 5 节）；查库期间这个线程在等网络响应，把 CPU 让给别人（第 2 节的阻塞让出）。多个请求同时打同一个 short code 时，SingleFlight 让后来的线程等第一个的查询结果（第 4 节用 jstack 看它们的状态）。
7. **响应写回**。`write()` 再次陷入内核，字节进 socket 发送缓冲区，网卡 DMA 取走发出去。连接如果是 keep-alive（HTTP 复用一条已建立的连接发多个请求，处理完不断开），就回到 Poller 继续被多路复用盯着。

这七步覆盖了本章全部概念。下面逐节展开。

## 进程与线程：资源单位与调度单位

### 先遇到问题

两个疑问，没有进程机制都答不了：为什么你的 Java 程序崩了，MySQL 还活着？为什么两个程序不能直接读写对方的内存？

答案是进程隔离。OS 给每个进程一套独立的虚拟地址空间和独立的资源表。MySQL 写坏自己的内存，碰不到 JVM 的内存。

### 准确定义

**进程**是 OS 分配资源的单位。进程拿到：一份独立虚拟地址空间（第 6 节细讲）、一张文件描述符表（第 5 节）、一个 PID（进程号）。进程不负责执行，它只是容器。

**线程**是 OS 调度 CPU 的单位。一个进程里至少有一个线程；每个线程有自己的栈和寄存器上下文，但**共享**所属进程的地址空间和文件描述符表。所以线程间传数据不用走 IPC（进程间通信），写同一个变量就行，这也是线程间会互相踩数据的原因（[13-concurrency.md](13-concurrency.md) 全章在处理这个后果）。

| | 进程 | 线程 |
|---|---|---|
| 地址空间 | 独立 | 共享所属进程的 |
| 文件描述符表 | 独立 | 共享所属进程的 |
| 栈、寄存器 | 各自一份 | 各自一份 |
| 一个崩溃影响另一个吗 | 不影响（隔离） | 影响（共享堆，OOM 全进程死） |

Java 里 `new Thread()` 创建的默认是平台线程。在 HotSpot 上（主流平台的实现，非语言规范强制），一个 Java 线程对应一个 OS 线程，由内核调度。

### 上下文切换：什么时候发生，贵在哪里

CPU 核数少于线程数，所以内核按时间片轮流让线程上 CPU。**上下文切换**就是换人：把当前线程的寄存器保存到内存，装入下一个线程的寄存器，切到它的内核栈继续。

切换发生在三种时机：时间片用完；更高优先级的线程就绪，抢占；当前线程主动让出：阻塞在 IO 上、等锁、`sleep`。第三种是后端服务的常态：处理 HTTP 请求的线程大部分时间都在等数据库返回。

切换的成本分两层：

1. **直接成本**：保存恢复寄存器、换内核栈。微秒量级（经验量级判断，非本机实测）。
2. **间接成本（大头）**：缓存变冷。CPU 缓存里存着上一个线程的工作数据，换人后这些数据对新线程没用，它要重新从内存读。进程间切换更贵：地址空间都换了，页表也要换，TLB（CPU 缓存页表翻译结果的硬件，第 6 节会用到页表概念）大面积失效。

推论：CPU 密集任务把线程数开到超过核数，不会更快，只会增加切换次数。IO 密集任务可以远超核数，因为大部分线程在睡觉，不上 CPU。线程数怎么定，[13-concurrency.md](13-concurrency.md) 有完整推导。

### 演示一：让程序自己报告六种线程状态

Java 给每个线程一个状态值（语言层抽象，不是 OS 的进程状态）。下面的程序造出五种典型状态，然后打印。代码里 `() -> { ... }` 是 lambda 表达式，用来现场给出线程要执行的代码块，语法见 [java/10-08-lambda-stream-optional.md](java/10-08-lambda-stream-optional.md)。

```java
public class ThreadStatesDemo {
    static final Object LOCK = new Object();
    static final Object WAIT_LOCK = new Object();

    public static void main(String[] args) throws Exception {
        Thread sleeper = new Thread(() -> {
            try { Thread.sleep(120_000); } catch (InterruptedException e) { }
        }, "t-sleeping");
        sleeper.setDaemon(true);
        sleeper.start();

        Thread waiter = new Thread(() -> {
            synchronized (WAIT_LOCK) {
                try { WAIT_LOCK.wait(); } catch (InterruptedException e) { }
            }
        }, "t-waiting");
        waiter.setDaemon(true);
        waiter.start();

        Thread holder = new Thread(() -> {
            synchronized (LOCK) {
                try { Thread.sleep(120_000); } catch (InterruptedException e) { }
            }
        }, "t-holder");
        holder.setDaemon(true);
        holder.start();

        Thread busy = new Thread(() -> {
            long x = 0;
            while (true) { x++; }
        }, "t-busy");
        busy.setDaemon(true);
        busy.start();

        Thread contender = new Thread(() -> {
            synchronized (LOCK) { }
        }, "t-blocked");
        contender.setDaemon(true);

        while (holder.getState() != Thread.State.TIMED_WAITING) { Thread.sleep(5); }
        contender.start();
        while (contender.getState() != Thread.State.BLOCKED) { Thread.sleep(5); }
        while (waiter.getState() != Thread.State.WAITING) { Thread.sleep(5); }

        Thread neverStarted = new Thread(() -> { }, "t-new");
        System.out.println("t-busy     -> " + busy.getState());
        System.out.println("t-sleeping -> " + sleeper.getState());
        System.out.println("t-waiting  -> " + waiter.getState());
        System.out.println("t-blocked  -> " + contender.getState());
        System.out.println("t-holder   -> " + holder.getState());
        System.out.println("t-new      -> " + neverStarted.getState());
    }
}
```

```text
t-busy     -> RUNNABLE
t-sleeping -> TIMED_WAITING
t-waiting  -> WAITING
t-blocked  -> BLOCKED
t-holder   -> TIMED_WAITING
t-new      -> NEW
```

逐行解释：

- `t-busy` 是 `RUNNABLE`：死循环数数，随时在 CPU 上跑。
- `t-sleeping` 是 `TIMED_WAITING`：`Thread.sleep(120_000)` 睡两分钟，睡够了会自己醒，所以是「带时限的等待」。
- `t-holder` 也是 `TIMED_WAITING`：它先抢到了 `LOCK`（进 `synchronized` 块），然后抱着锁睡觉。锁在它手里。
- `t-blocked` 是 `BLOCKED`：它也想进 `synchronized (LOCK)`，但锁被 t-holder 抱着，进不去。BLOCKED 专指「等锁」。
- `t-waiting` 是 `WAITING`：它对 `WAIT_LOCK` 调了 `wait()`，在等别人唤醒它，不限时。注意它等的是「被通知」，不是「等锁」，所以状态和 t-blocked 不同。
- `t-new` 是 `NEW`：`start()` 还没调用，OS 里根本没有这个线程。

程序逐个等待目标状态出现再打印（那三个 `while` 轮询），所以输出是确定的，不是碰运气。所有线程都设了 daemon（守护线程），main 一结束 JVM 就退出，不会真的挂两分钟。

### 演示二：用 jstack 从外部看一个活进程

程序自己报状态是自检。真实排障时你看的是**别人家**的进程，工具是 `jstack`：JDK 自带的线程转储工具，把目标 JVM 里所有线程此刻的状态和调用栈打出来。

下面这个程序会活 25 秒，期间你从另一个终端对它执行 jstack。

```java
public class ThreadFarmDemo {
    static final Object LOCK = new Object();
    static final Object WAIT_LOCK = new Object();

    public static void main(String[] args) throws Exception {
        System.err.println("pid " + ProcessHandle.current().pid());

        Thread busy1 = new Thread(ThreadFarmDemo::spin, "t-busy-1");
        Thread busy2 = new Thread(ThreadFarmDemo::spin, "t-busy-2");
        Thread sleeper = new Thread(() -> {
            try { Thread.sleep(120_000); } catch (InterruptedException e) { }
        }, "t-sleeping");
        Thread holder = new Thread(() -> {
            synchronized (LOCK) {
                try { Thread.sleep(120_000); } catch (InterruptedException e) { }
            }
        }, "t-holder");
        Thread waiter = new Thread(() -> {
            synchronized (WAIT_LOCK) {
                try { WAIT_LOCK.wait(); } catch (InterruptedException e) { }
            }
        }, "t-waiting");
        Thread contender = new Thread(() -> {
            synchronized (LOCK) { }
        }, "t-blocked");

        busy1.setDaemon(true);
        busy2.setDaemon(true);
        sleeper.setDaemon(true);
        holder.setDaemon(true);
        waiter.setDaemon(true);
        contender.setDaemon(true);

        busy1.start();
        busy2.start();
        sleeper.start();
        holder.start();
        while (holder.getState() != Thread.State.TIMED_WAITING) { Thread.sleep(5); }
        waiter.start();
        contender.start();
        Thread.sleep(200);

        System.err.println("observe me for 25 seconds (jstack / tasklist)");
        Thread.sleep(25_000);
    }

    static void spin() {
        long x = 0;
        while (true) { x++; }
    }
}
```

```text
输出（示意）：
pid 34332
observe me for 25 seconds (jstack / tasklist)
```

两行都打在 stderr（诊断信息的习惯去处），`pid` 每次运行都不同，所以标了示意。pid 是 OS 给进程的编号，之后所有外部观察都靠它。

怎么读这份转储，逐列说：

- 行首双引号是线程名。给关键线程起名字，就是为了在这里一眼认出来。
- `cpu=3250.00ms elapsed=3.50s`：t-busy-1 出生 3.5 秒，烧了 3.25 秒 CPU。两个 busy 线程各烧各的，互不等待：它们被内核放在两个核上并行了。这就是多线程的物理意义。

### 项目的线程模型：一个 JVM 里到底有多少线程

LinkForge 应用跑起来，转储里能看到的线程至少有四类（框架行为加项目代码，均已核实）：

1. **Tomcat 工作线程**，名字形如 `http-nio-8080-exec-1` 到 `exec-200`。Spring Boot 嵌入式 Tomcat 默认线程池上限 200（框架默认值；`src/main/resources/application.yml` 没有配置 `server.tomcat` 任何项，默认值原样生效）。第 4 节会讲这个数字和连接数的关系。
2. **`cache-evictor`**：项目自己起的单线程定时器。`src/main/java/com/linkforge/link/service/ShortLinkService.java` 第 80 行用 `Executors.newSingleThreadScheduledExecutor` 创建，线程工厂里显式命名为 `cache-evictor` 并设为 daemon。
3. **Spring 调度线程**：`src/main/java/com/linkforge/observability/BacklogGauges.java` 用 `@Scheduled` 每 15 秒（配置 `linkforge.metrics.backlog-sample-interval-ms`，默认 15000）对数据库跑三条 COUNT，把结果写进指标。这个任务的执行者也是一条常驻线程。
4. **GC 线程组**：上面演示二里数过的那批。

还有一个容易被误读成「多线程并发查库」的地方：`src/main/java/com/linkforge/link/support/SingleFlight.java` 第 57 行的 `run` 方法。并发请求同一个 short code 时，第一个到的人（leader）**在自己这条请求线程上**同步查库，没有另开线程；后来的人（follower）调 `existing.get(500)` 等他的结果。等待的这最多 500 毫秒里，follower 的请求线程处于 `TIMED_WAITING`（据代码推断，超时参数来自配置 `wait-timeout-ms: 500`）。用演示二的方法对应用进程做 jstack，能看到成批 `http-nio-8080-exec-*` 线程停在同一处。这就是「一个请求占一个线程直到结束」在真实项目里的样子。

## 用户态与内核态：每次系统调用都在过安检

### 先遇到问题

你的程序为什么不能自己从网卡拿数据、自己往磁盘写文件，非要「告诉」OS？

因为一台机器上跑着互不信任的程序。如果应用能直接操作网卡，它就能抢走别的程序的数据包；能直接写磁盘，就能改掉别人的文件。所以 CPU 把指令分了两级：**用户态**（应用程序跑的地方，特权指令被禁止，碰不了设备和别的进程内存）和**内核态**（内核代码跑的地方，什么都能做）。这是 CPU 硬件提供的保护机制（OS 规范语义），不是 Linux 独有。可以把系统调用想成「过安检」，但要记住比喻的边界：安检查的是「你要办什么事」并决定是否代办，不检查数据内容；而且每一次调用都要重新过，没有快速通道。

### 系统调用是什么

应用程序想干任何「出格」的事（读文件、收发包、建线程、取当前时间）只能走**系统调用**（syscall）：一条特殊指令把 CPU 切到内核态，内核代为执行，再把结果和 CPU 还给用户态。`read()`、`write()`、`open()`、`socket()`、`connect()` 都是系统调用。第 1 节的七个动作里，步骤 5 和 7 各是一次 syscall。

**代价从哪来**：这不是普通函数调用。要保存用户态现场、切换到内核栈、内核还要检查你的参数（防止传个野指针进来），做完再切回来。比一次普通函数调用贵两个数量级左右（量级判断，非本机实测），而且 JIT 再聪明也优化不掉它。另外注意：syscall 造成的是**模式切换**，不一定换线程；上下文切换是换线程执行。两个词不能混用，面试常考。

### 推论：攒一批再问

syscall 贵，结论就是少问、一次多要。读文件时用 8KB 的缓冲区一次读完，和循环 8000 次、每次读 1 字节，内核做的事一样多，但前者只付一次过安检的钱。Java 标准库的 `BufferedInputStream`、`BufferedReader` 存在的全部理由就是把很多次小 syscall 攒成少数几次大 syscall（库行为）。

想数一数一个进程每秒做了多少次 syscall：Linux 上用 `strace -c -p <pid>`（Linux 工具，本机 Windows 没有，面试与服务器上都会遇到）。高 `%sy`（见第 8 节）时它就是取证工具。

## IO 模型：线程到底阻塞在哪里

### 先遇到问题

假设一万个客户端同时连着你的服务。最朴素的写法：一个连接开一个线程，线程里循环 `read()`。一万个线程意味着什么？每个线程一条调用栈，HotSpot 在常见 64 位平台默认栈大小约 1MB，光栈就是 10GB 量级的内存承诺；内核调度表里一万个实体。这条朴素路线就是 **BIO（阻塞 IO）**，它的瓶颈不在「慢」，在于**每个等待中的连接都要押上一个线程**。

### BIO 阻塞在哪里

线程调用 `read()`，内核里这个 socket 还没有数据。此时内核把线程挂起（移出调度队列，不占 CPU），数据到达、拷贝进缓冲区后再唤醒线程。这就是阻塞：调用没返回，线程睡在内核里。阻塞期间不烧 CPU，但**栈和线程本身都占着资源**。

一个反直觉的细节，面试常考：**阻塞在 socket 读上的线程，在 jstack 里显示 `RUNNABLE`**，栈顶形如 `java.net.Socket$SocketInputStream.read` 下面的 `socketRead0`。因为「RUNNABLE」在 Java 语义里是「不在 Java 层的锁或等待点上」，线程已经进了 native 代码，JVM 不再管它的生死。所以读线程转储不能只看状态列，**要看栈顶**：栈顶在 `socketRead0`/`socketWrite0` 的 RUNNABLE，其实是在等网络。

### 多路复用：一个线程盯一堆连接

思路反过来：让**一个**线程同时盯着所有连接，谁的数到了谁被挑出来，再把就绪的活分给工作线程。前提是内核提供一个「监视很多 fd」的系统调用（fd 概念第 5 节，不依赖先后顺序，可先理解为「连接的编号」）。

- **select/poll**（Linux 实现）：每次调用把整批 fd 从用户态拷进内核，内核线性扫一遍，返回后用户再挨个问「你好了吗」。连接多时，拷贝和扫描本身就成了开销。
- **epoll**（Linux 实现）：把 fd 集合在内核里登记一次；每个 fd 有数据时内核把它挂到就绪列表；应用每次调用只拿走「就绪的那些」，开销正比于就绪数而不是总连接数。高连接、低活跃场景下差距巨大。
- Windows 的等价机制叫 IOCP，名字不同，思想相同（就绪事件交给线程池）。

Redis 用单线程加 epoll 支撑大量客户端连接，是这套机制最著名的应用（[50-redis.md](50-redis.md)）。Netty、Nginx 同理。

### Tomcat 到底是不是「一个连接一个线程」

这里要修正一个流传很广的说法。Spring Boot 3.3 嵌入的 Tomcat 默认用的是 NIO connector（框架行为，官方文档写明）：连接由 Poller 用多路复用统一盯着，**空闲的 keep-alive 连接不占任何工作线程**；只有产生了可处理的请求，才从线程池借一个线程。

所以「Tomcat 一个连接一个线程」是过时描述（那是 Tomcat 8.5 之前 BIO connector 的行为）。准确的说法是：**传输层是多路复用，处理层是一个请求占一个线程直到结束**。处理期间，你的业务代码里每一次 JDBC 查询、每一次 Redis 调用都是阻塞 IO，都把这个线程押在原地。业界口语说的「Tomcat 是 BIO 模型」，指的是这个**同步阻塞的处理模型**，不是传输层。这也解释了两件事：

1. 线程池上限（Spring Boot 默认 200）是处理并发度的硬顶：第 201 个并发请求在队列里排队（默认还能排 100 个，再往后拒绝连接）。注意这是 200 个**请求**，不是 200 个**连接**，连接数上限是另一个默认值 8192。
2. 想撑更高的并发，方向是让单请求更快（缓存、合并，本项目的 Redis 缓存和 SingleFlight 都在给线程减负），或者换处理模型（Netty 的回调式、Java 21 的虚拟线程）。本项目用 Java 17，虚拟线程不可用，也未引入 Netty，如实说。

## 文件描述符：一切皆文件与 fd 泄漏

### 先遇到问题

服务平稳跑了三天，突然拒绝所有连接，日志里是 `Too many open files`。进程没崩、内存正常。这类故障的根源是一个平时没人看的小表：文件描述符表。

### 准确定义

**文件描述符**（fd，file descriptor）是一个非负整数，是进程「打开文件表」的数组下标。进程每打开一个东西，内核在表里给它一个空位，把下标返回给程序；程序之后用这个整数指代那个打开的东西。fd 0、1、2 固定是标准输入、输出、错误。

「一切皆文件」是 Linux 的设计语义：普通文件、目录、socket、管道、终端设备，打开后都领一个 fd，读写的接口长得一样。所以**每条 TCP 连接也是一个 fd**。fd 不还（不 close）就一直占着表位；表满了再打开就报 `Too many open files`。上限用 `ulimit -n` 查看（每进程限制，软限可调高到硬限）。

Windows 的对应物叫**句柄**（handle）。语义是近亲（打开的东西领一个整数凭据），但内容更杂：线程、事件对象、堆内部节、注册表键都算句柄。所以 Windows 的句柄数和 Linux 的 fd 数不能直接对表，看趋势和增量才有意义（平台差异，标注）。

### 演示：把 fd 表撑出可见的增量

下面的程序故意打开 n 个文件不关（真实事故里这就是「流没 close」的样子），然后活着等你来数。参数为 0 时一个也不开，做对照组。

```java
import java.io.FileInputStream;
import java.io.File;
import java.nio.file.Files;

public class FdLeakDemo {
    public static void main(String[] args) throws Exception {
        int n = args.length > 0 ? Integer.parseInt(args[0]) : 2000;
        File f = File.createTempFile("leak", ".txt");
        Files.writeString(f.toPath(), "hello");
        FileInputStream[] neverClosed = new FileInputStream[n];
        for (int i = 0; i < n; i++) {
            neverClosed[i] = new FileInputStream(f);
        }
        System.out.println("opened " + n + " file streams without closing them");
        System.err.println("pid " + ProcessHandle.current().pid());
        Thread.sleep(20_000);
    }
}
```

```text
opened 2000 file streams without closing them
```

打开一个 `FileInputStream` 就是立即在内核里登记一个文件句柄（构造器里就完成，不是懒加载）；数组 `neverClosed` 握着全部引用，垃圾回收碰不到它们。pid 打在 stderr，程序活 20 秒给你观察窗口。

本机两次真实运行（Git Bash，另一个终端用 PowerShell 数句柄，`HandleCount` 是进程句柄总数）：

```text
$ java FdLeakDemo 0
opened 0 file streams without closing them        # 本次 pid 34756

$ powershell -NoProfile -Command "(Get-Process -Id 34756).HandleCount"
288

$ java FdLeakDemo 2000
opened 2000 file streams without closing them     # 本次 pid 27980

$ powershell -NoProfile -Command "(Get-Process -Id 27980).HandleCount"
2288
```

2288 减 288 正好等于 2000：**每开一个文件流，句柄数精确加一**。基线 288 不是零，是 JVM 自身（线程、堆内部节、各类内核对象）本来就握着的句柄（Windows 实现细节，基线随 JDK 版本浮动，据运行观察推断）。

Linux 服务器上看同一现象的命令（原文给出，供上机使用）：

```text
ls /proc/<pid>/fd | wc -l      # 这个进程现在握着几个 fd
lsof -p <pid>                  # 每个 fd 对应打开的什么（网络连接也在里面）
cat /proc/<pid>/limits | grep "open files"   # 这个进程的 fd 上限
```

`/proc` 是 Linux 把内核数据暴露成文件的机制，`/proc/<pid>/fd` 目录下每个文件名就是一个 fd 号。Git Bash 里没有它们，别怀疑装错了。

### 泄漏怎么防

泄漏 = 打开不关。Java 的防线是 try-with-resources：把打开动作写进 `try (...)` 的括号里，无论正常返回还是抛异常，编译器生成的代码保证 close 被调用。初学者常犯的写法是把 close 写在 try 块最后一行，中间一旦抛异常，close 永远执行不到，fd 就漏了。另一个隐性泄漏源是连接池没配回收：每个连接是 fd，池子无限增长迟早打爆上限。

### 项目对照

本项目里每个外部依赖的连接都是 fd：MySQL 连接池的每条连接、Redis 的每条连接、RabbitMQ 的每条连接，在进程 fd 表里各占一格（据代码与配置推断：连接池由框架管理，应用代码不直接碰 fd）。`docker-compose.yml` 的三个 healthcheck 每 10 秒各自新开一次连接做探测，探测完关闭，这是短命 fd 的常态。给连接池设上限，本质上就是在给 fd 表设预算。

## 虚拟内存、RSS 与容器内存

### 先遇到问题

两个问题没有虚拟内存都答不了：两个程序都想用内存地址 `0x1000`，谁让谁？物理内存 8GB，跑着的进程们「以为」自己有那么多内存，多出来的部分是什么？

### 页表与缺页：概念级

每个进程拿到的是**虚拟地址空间**：一整条自己的地址线，程序里所有指针都是虚拟地址。虚拟地址不能直接用，要靠**页表**翻译：内存按 4KB 切成页，页表记录「这个进程的第 N 个虚拟页 → 物理内存的第 M 个页框」。CPU 里的 MMU 硬件在每次访存时查表（TLB 缓存查过的表项，所以翻译通常不慢）。每个进程一张自己的页表，这就是进程隔离在硬件层的实现，也是进程切换贵的原因之一（换页表，TLB 大面积失效）。

两个关键机制：

- **按需分页**：程序申请 1GB 内存，内核不会立刻给 1GB 物理页，只在页表里登记虚拟范围。第一次真正访问某页时，MMU 查不到映射，CPU 触发**缺页异常**，内核补一个物理页框、填好页表、重跑那条指令。缺页是日常机制不是错误；只有当缺页频繁到「每次都要从磁盘读页」时才是性能灾难。
- **swap**：物理内存吃紧时，内核把不活跃的页写到磁盘腾地方。后端服务（数据库、JVM）通常显式关 swap：关键页一旦被换出，每次访问从内存级延迟掉到磁盘级，延迟变得不可控，宁可内存不足时快速失败（常见工程约定，非规范强制）。

### RSS 与 JVM 堆：不是一回事

**RSS**（resident set size，常驻集）是进程此刻实际占用的物理内存量。Linux 的 `top`/`ps` 看到的就是它；Windows 的对应物是工作集（working set）。

JVM 进程的 RSS 由几块拼起来：Java 堆（`-Xmx` 限的只是它）＋ 元空间 ＋ 每线程一条的栈 ＋ GC 自己的记账结构 ＋ 直接内存 ＋ JVM 可执行体自身。所以 **`-Xmx` 不等于进程内存上限**，给容器里的 JVM 排内存预算时要全部算进去。

本机实测佐证：上面演示二那个 7 个自建线程、堆里几乎没放数据的玩具程序，进程内存是这样的：

```text
$ tasklist //FI "PID eq 35868"

映像名称                       PID 会话名              会话#       内存使用
========================= ======== ================ =========== ============
java.exe                     35868 Console                    1     39,828 K
```

用 PowerShell 读同一个进程的工作集：`WorkingSet MB: 38.9`。tasklist 的「内存使用」列和 WorkingSet 是同一物（本机验证过，两个数一致）。39MB 几乎全是 JVM 自身结构和线程栈，堆数据接近零。这说明「看堆里有什么」和「看进程占多少内存」是两个问题。

### 容器内存限制与 OOMKill

容器是「受限的进程」（第 2 节的进程概念加两层机制）：namespace 隔离视图（自己的 PID 序号、网络栈、挂载点），**cgroup**（内核的资源记账与限额机制）限制用量。给容器设内存上限，本质是内核在 cgroup 里记账：这个组用超了，内核的 OOM killer 选一个牺牲进程直接 SIGKILL。

于是容器里 JVM 的「内存溢出」有两种完全不同的死法，区分它们是排障基本功：

- **`java.lang.OutOfMemoryError`**：JVM 自己发现堆装不下了，抛异常、打栈、进程可能还活着。这是 JVM 内部的事。
- **OOMKill**：cgroup 配额被整个进程（堆外的部分也算）撑破，内核直接杀，无任何 Java 异常、无堆栈。特征是进程无声消失；容器场景下 `docker inspect` 能看到 `State.OOMKilled: true`，退出码 137（128 加信号 9，见第 9 节信号的编码习惯）。

现代 JVM 会主动读 cgroup 配额来算默认堆大小（HotSpot 的 UseContainerSupport，JDK 10 起默认开启），但这不等于安全：堆只是进程内存的一部分，堆外涨起来照样触发 OOMKill。

**项目现状如实说**：`docker-compose.yml` 里没有给 mysql、redis、rabbitmq 配任何内存限制（没有 `deploy.resources.limits`，也没有 `mem_limit`），三个容器按需使用宿主机内存。这是本机开发环境的项目选择，不是容器默认行为；生产部署一般要显式限额并把限额写进告警（部署侧话题见 [61-docker-deploy.md](61-docker-deploy.md)）。诊断时也不要在宿主机上用 `free` 判断容器水位：容器限额看 `docker stats`，宿主 free 只是宿主视角。

Linux 上看系统内存用 `free -h`，其中 `available` 列比 `free` 列更有意义：available 是「不引发换页还能拿来用的量」，free 只数完全空闲的页。

## 零拷贝：sendfile 少跑两趟

### 先遇到问题

把磁盘上一个 100MB 文件发给网络对端（下载服务、消息系统搬日志段），最直白的写法是 `read` 进字节数组再 `write` 出去。这份数据在机器里搬了几次家？

### 传统 read + write：四次拷贝

以 Linux 实现为背景（各 Unix 类似）：

1. DMA（硬件直接搬运用，不占 CPU）把磁盘数据搬进内核的**页缓存**（内核为文件内容留的内存页，第 6 节的页概念）。
2. CPU 把页缓存搬进**用户区**，你的字节数组这才拿到数据（这是 `read()` 返回的时刻）。
3. CPU 把用户区数据搬进内核的 **socket 发送缓冲**（这是 `write()` 做的事）。
4. DMA 把 socket 缓冲搬上网卡。

两次系统调用、四份搬运，其中第 2、3 步是 CPU 干的纯粹搬运工，数据在用户区根本没被加工过。**零拷贝的「零」指的是省掉进用户区的 CPU 拷贝**，不是一次拷贝都没有。

### sendfile：数据不出内核

Linux 提供了 `sendfile` 系统调用：告诉内核「把 fd A 的这段内容送进 fd B」，数据在内核里从页缓存直达 socket 缓冲（网卡支持 scatter-gather 时更省，socket 侧只写元数据）。一次系统调用，两次模式切换变一次，CPU 拷贝归零。

Java 对应的 API 是 `FileChannel.transferTo`。下面的程序生成一个 16MB 临时文件，用 transferTo 复制到另一个文件：

```java
import java.io.RandomAccessFile;
import java.nio.channels.FileChannel;
import java.nio.file.Files;
import java.nio.file.Path;

public class ZeroCopyDemo {
    public static void main(String[] args) throws Exception {
        Path src = Files.createTempFile("zc-src", ".bin");
        Path dst = Files.createTempFile("zc-dst", ".bin");
        byte[] chunk = new byte[8192];
        try (var out = Files.newOutputStream(src)) {
            for (int i = 0; i < 2048; i++) {
                out.write(chunk);
            }
        }
        long size = Files.size(src);
        try (FileChannel in = new RandomAccessFile(src.toFile(), "r").getChannel();
             FileChannel outCh = new RandomAccessFile(dst.toFile(), "rw").getChannel()) {
            long copied = in.transferTo(0, size, outCh);
            System.out.println("source bytes: " + size);
            System.out.println("copied bytes: " + copied);
            System.out.println("target matches: " + (Files.size(dst) == size));
        }
    }
}
```

```text
source bytes: 16777216
copied bytes: 16777216
target matches: true
```

边界要说清：本机是 Windows，JVM 在 Windows 上映射的是 TransmitFile 而不是 sendfile（平台实现差异），这个演示验证的是 **API 行为**（一次调用、内核路径搬运、字节精确到达），不是 sendfile 本身。Linux 服务器上同一个调用才由 HotSpot 落到 sendfile。另外零拷贝有适用范围：内容需要在用户区加工时（压缩、加密、改写）用不上，数据必须先回用户区。Kafka、nginx 这类以文件搬运为核心负载的系统公开说明使用了这条路径（据公开资料，生态常识）。

## 负载与 CPU：load 平均值和 top 怎么读

### load average：不是 CPU 利用率

「服务器很卡」的第一眼通常是 load。**load average** 是「可运行实体数 + 不可中断睡眠实体数」的指数加权平均，分别取 1、5、15 分钟窗口（Linux 实现；Linux 把不可中断的磁盘等待 D 状态也计入，这一点与其他 Unix 不同，跨平台比较时要注意）。「可运行」是在排队上 CPU 的，「不可中断睡眠」是被磁盘 IO 押住的。所以 load 高有两种成因：CPU 排队，或磁盘排队。

**标尺是核数**。4 核机器 load 4.0 是满载边界；load 8.0 意味着平均每个核后面排着一倍的队。判断高不高永远先除以核数，再看 1 分钟与 15 分钟的相对走势（1 分钟高于 15 分钟说明正在恶化）。

### top 的 CPU 列

`top`（Linux）进程行里最有诊断价值的是 CPU 分解：`%us`（用户态，你的业务代码）、`%sy`（内核态，syscall 与内核事务）、`%id`（空闲）、`%wa`（等 iowait：CPU 空闲但有没有完成的磁盘 IO）。判读方向：`%us` 高找业务热点；`%sy` 高说明内核在替你干太多活：syscall 太碎、上下文切换太频繁、网络包太小，优化方向是批量化而不是加线程；`%wa` 高是磁盘在拖。

`top -H -p <pid>` 把同一进程按线程拆开（Linux 命令），找到烧 CPU 的线程号后转成十六进制（`printf '%x' <线程号>`），去 jstack 转储里对 `nid` 定位它此刻在干什么。这套「top 定位线程、jstack 定位栈」是线上 CPU 排查的标准两步。

Windows 上没有 load average（没有对应导出），等价物：任务管理器「详细信息」页看进程 CPU 与线程数；`tasklist` 看内存；PowerShell 的 `Get-Process` 能读进程累计 CPU 时间。

### 实测：CPU 时间可以跑赢墙钟

对演示二的程序（两个死循环线程）做一次真实观察。程序启动约 8 秒后：

```text
$ powershell -NoProfile -Command "$p = Get-Process -Id 35868; Write-Output ('CPU seconds: ' + [math]::Round($p.CPU, 1)); Write-Output ('WorkingSet MB: ' + [math]::Round($p.WorkingSet64/1MB, 1))"
CPU seconds: 15.7
WorkingSet MB: 38.9
```

（Git Bash 里写 PowerShell 命令要给 `$` 加反斜杠防止 bash 抢先展开，如上。）

墙钟过了约 8 秒，进程累计烧了 15.7 秒 CPU。因为两个线程在两个核上同时跑，CPU 时间是按核累加的，可以超过墙钟。这也说明 CPU 时间和 load 是两套计量：CPU 时间是进程记账，load 是调度队列长度的平均。Linux 上同样的观察用 `ps -o cputime -p <pid>` 或 `top` 里的 `TIME+` 列。

## 进程的属性：环境变量、时钟、信号

进程不只是「代码加线程」这三样，还有几个常被忽略的系统属性，本项目都在它们身上踩过坑。

**环境变量是创建时的快照**。进程创建那一刻，从父进程复制一份环境变量，之后与父进程再无联系。所以 `.env` 文件躺在磁盘上对 JVM 没有任何作用：`source .env` 把变量注入当前 shell，随后这个 shell 里启动的 `java -jar` 才继承到；换一个终端窗口，新 shell 没这批变量，服务就「神秘地」缺配置。仓库 README 给 PowerShell 和 bash 两套写法，原因就是这个（LinkForge 项目文档事实）。

**时钟取自 OS 配置**。JVM 的 `LocalDateTime.now()` 读 OS 时区（可用 `-Duser.timezone` 覆盖），MySQL 的 `NOW()` 用容器时区。本项目真实事故 Bw2-M1：JVM 在 +8 时区、MySQL 容器在 UTC，退避时间差 8 小时，20 秒的重试间隔被拉成 8 小时（事故与修复见 [51-rabbitmq-outbox.md](51-rabbitmq-outbox.md)）。时区不是格式化问题，是系统配置。

**信号的两种死法**。`SIGTERM` 是礼貌请求：进程可以捕获它，停止接新请求、处理完在途请求、释放连接和线程池，然后退出，这就是优雅停机。`SIGKILL`（`kill -9`）是内核直接回收，进程收不到任何通知，**所有清理代码都不会执行**。本项目 `ShortLinkService.java` 第 86 行的 `@PreDestroy void shutdownEvictor()` 就是一个清理钩子：收到 TERM 时 Spring 容器关闭前调用它，停掉 `cache-evictor` 定时线程。进程若被 `kill -9`，这类钩子根本不跑。所以重启的正确姿势是先 TERM、等优雅退出、超时才升级 KILL（Docker 的 stop 默认也是先 TERM，等 10 秒超时才 KILL，Docker 默认行为）。退出码 137（128+9）就是「被 KILL 杀掉」的记号，看到它先想 OOMKill 和强杀。

## Linux 排查命令速查与 Windows 对照

按场景记，不按字母背。每条命令背后都是本章讲过的一块 OS 机制。

| 场景 | Linux 命令 | 看什么（对应机制） |
|------|------|--------|
| 进程活着吗 | `ps aux \| grep java`、`docker compose ps` | PID、状态、healthy（第 2 节进程） |
| 端口在听吗 | `ss -tlnp \| grep 8080` | LISTEN 状态与进程号（第 1 节步骤 2） |
| CPU 高 | `top`，`top -H -p <pid>` 看线程 | %us/%sy 分解；线程号转十六进制配 jstack（第 8 节） |
| 负载 | `uptime`、`cat /proc/loadavg` | load 三值除以核数（第 8 节） |
| 内存 | `free -h`、`cat /proc/<pid>/status` | available；RSS 与 JVM 堆的区别（第 6 节） |
| 磁盘满 | `df -h`、`du -sh *` | Docker 卷与日志是常见元凶 |
| fd 泄漏 | `ls /proc/<pid>/fd \| wc -l`、`lsof -p <pid>` | fd 数与上限（第 5 节） |
| 网络 | `ping`、`curl -v`、`ss -s` | 连通、握手细节、连接总数（[20-network.md](20-network.md)） |
| 日志 | `tail -f`、`grep -i error`、`journalctl` | 从最后一个 `Caused by` 读起 |
| 信号 | `kill -TERM <pid>` | 先礼后兵；`kill -9` 是最后手段（第 9 节） |
| syscall 计数 | `strace -c -p <pid>` | 谁的系统调用最频繁（第 3 节） |

**Windows 读者注意**：本机 Git Bash 里 `ss`、`top`、`df`、`ulimit`、`strace` 都不存在，别怀疑自己装错了。等价替代：端口看 `netstat -ano | findstr 8080`；进程与线程用任务管理器的「详细信息」页（展开可见线程）；内存与 CPU 时间用 `tasklist` 与 PowerShell `Get-Process`（第 6、8 节已实测）；fd 用 PowerShell 句柄数（第 5 节已实测，注意语义差异）。`jstack`、`jps`、`jmap` 这些 JDK 工具 Windows 上直接可用。面试口径仍是 Linux 命令：背 Linux 版，本机用 Windows 版练流程。

排障的通用顺序：先确认进程与端口（活着吗、在听吗），再看错误日志（哪一层在报错），再看资源水位（CPU、内存、磁盘、连接），最后才看代码。与「从最后一个 Caused by 读栈」同构：先抓最内层的事实。

## 常见错误与误区

- **「线程越多越快」**。CPU 密集任务超过核数的部分只是在排队和切换，不会更快；IO 密集的上限取决于等待比例，最终靠压测定，不靠拍脑袋。
- **「jstack 里 RUNNABLE 就是在烧 CPU」**。阻塞在 socket 读上的线程也是 RUNNABLE，看栈顶才知道它是不是在等网络（第 4 节）。
- **「容器里的内存看宿主 free」**。容器限额是 cgroup 记账，看 `docker stats`；宿主 free 是宿主视角。判断 OOMKill 用 `docker inspect` 的 `State.OOMKilled`。
- **「swap 开着是兜底」**。关键页换出后延迟从内存级掉到磁盘级，连接池全线超时；数据库与 JVM 通常显式关 swap，宁可快速失败。
- **「kill -9 是万能重启术」**。它跳过全部清理，`@PreDestroy` 钩子不执行、在途请求被腰斩；先 TERM 等优雅退出，超时才升级。
- **「只有文件才占 fd」**。socket、管道、设备全占。连接数暴涨打爆 fd 表，报的是 `Too many open files`，看起来像「文件问题」，其实是连接问题。

## 面试常见问题与追问

**进程与线程的区别？什么场景必须多进程？**
资源单位对调度单位：进程独立地址空间与 fd 表，线程共享前者、各持栈与寄存器。必须隔离（容错、权限）时用多进程，浏览器一个页崩不拖全浏览器就是案例；高并发共享数据用多线程，代价是要处理竞态。追问「切换成本」：寄存器与内核栈是直接成本，缓存变冷与（进程间）页表切换是间接成本，后者更大。追问「怎么减少切换」：批量化减少阻塞点、减少锁竞争、协程或虚拟线程把等待留在用户态。

**BIO、NIO、多路复用的区别？Tomcat 用的哪个？**
BIO：一线程一连接，read 无数据时线程睡在内核，等待押上整条栈。多路复用：少数线程通过 epoll 这类机制监视全部 fd，只处理就绪的。Tomcat 默认 connector 传输层是多路复用（Poller），处理层是一个请求占一个线程直到结束、期间业务 IO 全部同步阻塞，这就是口语说的「BIO 模型」的准确含义。追问「epoll 比 select/poll 好在哪」：后两者每次全量拷贝 fd 集合加线性扫描，epoll 在内核维护注册表和就绪列表，开销正比于就绪数。追问「Redis 单线程为什么扛得住」：epoll 多路复用加纯内存操作。

**零拷贝省了什么？什么时候用不上？**
传统 read+write 四次拷贝两次系统调用，其中两次 CPU 拷贝把数据白搬进又搬出用户区；sendfile 让数据留在内核从页缓存直达 socket 缓冲，CPU 拷贝归零（Linux 实现；Java 的 `FileChannel.transferTo` 在 Linux HotSpot 上映射它）。用不上的场景：内容需要在用户区加工（压缩、加密、改写），数据必须先进用户区。追问「零拷贝是一次拷贝都没有吗」：不是，DMA 搬运仍在，省的是 CPU 拷贝与多余的模式切换。

## 自测

1. 为什么换一个终端窗口 `.env` 就「失效」了？
   答：环境变量是进程创建时从父进程复制的快照；`source` 只注入当前 shell，新 shell 没这批变量，它启动的 `java` 子进程自然也拿不到。
2. jstack 里一个线程显示 RUNNABLE，能断定它在烧 CPU 吗？
   答：不能。阻塞在 socket 读写上的线程也是 RUNNABLE，JVM 不追踪 native 层的挂起。要看栈顶：`socketRead0` 一类是等网络，真正的计算热点要看采样型工具或 `top -H` 交叉定位。
3. 容器里的 JVM 被 OOMKill 和抛 `OutOfMemoryError` 有什么区别？
   答：前者是内核 cgroup 记账超限后由 OOM killer 直接 SIGKILL，进程无声消失、无 Java 异常（`docker inspect` 可见 `OOMKilled: true`，退出码 137）；后者是 JVM 自己发现堆耗尽，有异常有栈、进程未必退出。容器内存预算要盖住堆加元空间、线程栈、直接内存，不只是 `-Xmx`。
4. fd 泄漏在 Linux 和 Windows 上分别怎么发现？为什么 Windows 的基线数不能直接和 Linux 比？
   答：Linux 看 `/proc/<pid>/fd` 数量随时间是否只涨不降、`lsof -p` 看每个 fd 是谁；Windows 用 PowerShell `HandleCount` 看增量趋势。Windows 句柄包含线程、事件等大量非文件对象，绝对值没有跨平台意义，增量才有。
5. 4 核机器 load average 是 5.0，说明什么？该看什么补充信息？
   答：平均有约 5 个实体在等资源，超出核数 1，存在排队。再分两个方向确认：`top` 看 `%us`（CPU 排队）还是 `%wa`（磁盘排队）高，1 分钟与 15 分钟对比看是在恶化还是恢复。
